### 2. 候选细节

#### #1 时间轮分层延迟消息

**当前 v0.1/v0.2 行为**（占位实现）：

```php
// src/Queue/KafkaQueue.php
public function later($delay, $job, $data = '', $queue = null)
{
    return $this->pushRaw(
        $this->createPayload($job, $this->connectionName, $data, $queue),
        $queue,
        ['delay_seconds' => max(0, (int) $delay)]
    );
}
```

只把 `x-available-at` 写到 header，消费端 `NativeHandler` 同步阻塞等待 → worker 被占死。

**v0.3 方案 A：时间轮分层 topic**（v0.1 §4.5 推荐，v0.3 落地）：

```
生产者:
  delay=5s   → 写 "delay-5s"   topic, header 标 "5s" 槽
  delay=30s  → 写 "delay-30s"  topic
  delay=60s  → 写 "delay-60s"  topic
  delay=300s → 写 "delay-300s" topic
  ...
消费者:
  5s  topic 消费 → 立刻 requeue 到主 topic
  30s topic 消费 → 等待 25s → requeue 到主 topic
  ...
```

`tiers[]` 在 `kafka.php` 配置：

```php
'delay' => [
    'tiers' => [5, 30, 60, 300, 1800, 3600, 86400],  // seconds
    'topic_prefix' => 'delay',                        // 生成 "delay-5s" 等
],
```

#### #2 批量消费

**v0.1/v0.2 行为**：单条 poll + 单条 handle。

**v0.3 方案**：

```php
// Consumer::pollBatch(int $max, int $timeoutMs): array
$messages = $consumer->pollBatch(50, 1000);  // 最多 50 条 / 最多等 1s
foreach ($messages as $message) {
    $result = $handler->handle($message);
    // batch 内统一 commit
}
$consumer->commit($messages);
```

`kafka:work` 加 `--batch-size=50 --batch-timeout=2000` 选项。

**约束**：

- 业务方 handler 必须**串行**或**自管理并发**（避免 offset 错乱）
- 整批处理完才 commit offset（at-least-once + 整批幂等）

#### #3 DLQ 高级

**v0.1 已有**：单 DLQ topic（`<topic>.dlq` 默认），9 个 DLQ 专属 header。

**v0.3 增强**：

| 增强 | 细节 |
| --- | --- |
| **按异常类型分 DLQ topic** | `config('kafka.connections.default.failed.dlq.topic_map')` 把异常类名 → DLQ topic |
| **DLQ 限速** | 每分钟 N 条，超过走"丢弃 + 报警"（避免 DLQ 爆） |
| **自动 replay 钩子** | 失败 N 次后**自动** requeue 回主 topic（替代人工） |
| **DLQ tail 命令** | `php artisan kafka:dlq:tail <dlq-topic>` 实时打印失败消息 |

#### #4 消息回放工具

**CLI**：

```bash
php artisan kafka:replay \
    --topic=orders.events \
    --from="-1h" \
    --to=now \
    --target-topic=orders.events.replay \
    --group=replay-runner
```

**实现路径**：

- 用独立 consumer group `replay-runner`（不影响主消费者）
- 时间窗口 `--from/-to` 解析为 Kafka offset（用 `offsetsForTimes`）
- re-produce 到 `--target-topic`
- 保留 `original_*` header

#### #5 性能基准

**目录**：`benchmarks/`

**工具**：

### 3. 兼容性影响

| 影响 | 范围 | 处理 |
| --- | --- | --- |
| **#1 时间轮** | `KafkaQueue::later` 行为变化 | 业务方 API 不变，内部从同步阻塞 → 异步 requeue |
| **#2 批量** | `Consumer::poll` 接口新增 `pollBatch` | 向后兼容（`poll` 还在），`kafka:work --batch-size` 默认 1 |
| **#3 DLQ 高级** | DLQ topic 数量从 1 → N（可选） | 向后兼容（业务方不开 `topic_map` 时走默认 `.dlq`） |
| **#4 Replay** | 纯新增 CLI | 无破坏 |
| **#5 基准** | 纯新增工具 | 无破坏 |

### 4. PHP 7.4 兼容约束（沿用 v0.2 经验）

- 不引入 PHP 8.0+ 特性（属性提升 / 命名参数 / enum / readonly）
- 闭包 / 数组函数 / 接口分离 / 值对象是 v0.3 的主武器
- 时间轮/批量/Replay 都是"**控制流 + IO**"逻辑，不依赖现代 PHP 特性

### 5. v0.3 不做的清单（明确推迟）

- ❌ **事务 Producer**（v0.4 评估）—— 跨 topic exactly-once，需评估 librdkafka transactional API
- ❌ **幂等性**（v0.4 评估）—— 需 `enable.idempotence=true` + 应用层 idempotency key
- ❌ **多 Consumer Group Fan-out**（v0.4 评估）—— 业务方场景不明确
- ❌ **Read-Committed**（v0.4 评估）—— 事务消费者
- ❌ **Schema Registry / Avro**（v0.4 评估）—— 生态集成
- ❌ **OpenTelemetry SDK**（v0.4 评估）—— 当前 `traceparent` header 手写已够用
- ❌ **Horizon / Octane 适配**（沿用 v0.1 决议，v0.4 重新评估）

## 替代方案

### v0.3 范围选择

| 方案 | 内容 | 评价 |
| --- | --- | --- |
| **A 全面 5 项** | 时间轮 + 批量 + DLQ 高级 + Replay + 基准 | 工作量大，预计 4-6 周 |
| **B 核心 3 项** | 时间轮 + 批量 + DLQ 高级 | 2-3 周，专注基础能力提升 |
| **C 核心 2 项** | 时间轮 + 批量 | 1-2 周，最高 ROI（吞吐 + 延迟） |
| **D 工具 2 项** | Replay + 基准 | 1 周，运维友好但不动核心 |

### 时间轮实现路径

| 路径 | 思路 | 评价 |
| --- | --- | --- |
| **方案 A：分层 topic**（v0.1 §4.5 推荐） | 5s / 30s / 60s / 300s / 1800s / 3600s / 86400s 多个 topic | 简单，Kafka 原生，运维直观 |
| 方案 B：单层时间轮（单 topic + 大量 partition） | 每条消息 header 写到期时间戳，worker 内存时间轮扫描 | 省 topic 但 worker 重启会丢内存状态 |
| 方案 C：Kafka delayed message（confluent） | 商业特性 | 不开源 |
| 方案 D：RabbitMQ-style TTL + DLQ 路由 | 复杂 | 不推荐 |

### 批量消费接口

| 接口 | 签名 | 评价 |
| --- | --- | --- |
| `pollBatch(int $max, int $timeoutMs): array<Message>` | 简单 | 业务方自己 for 循环 |
| `Worker` 模式（pull + handle + commit 整批） | 全自动 | 隐藏细节，难自定义 |
| 流式（Generator yield） | PHP 友好 | 内存友好但 offset commit 时机复杂 |

### Replay 入口

| 入口 | 思路 | 评价 |
| --- | --- | --- |
| **Artisan 命令** `kafka:replay` | v0.1 §4.8 描述 | 标准，运维友好 |
| Kafka Streams / KSQL 独立服务 | 重量级 | 过度设计 |
| 业务方 PHP 代码内调用 | 灵活 | 缺标准 CLI 入口 |

### 性能基准范围

| 范围 | 评价 |
| --- | --- |
| 仅自测（不对比 mateusjunges） | 简单，但缺外部参考 |
| **自测 + mateusjunges 对比**（Docker 同环境） | 客观，能定位差距 |
| 自测 + 对比 + 历史趋势（CI 跑分入库） | 重型，需额外基础设施 |
