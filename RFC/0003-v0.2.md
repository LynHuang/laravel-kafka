## 摘要

按"用户决议 C 综合路线"，v0.2 范围**横跨两条计划线**：

1. **借鉴线**（来自 [`对比分析_mateusjunges_vs_lynhuang.md`](../对比分析_mateusjunges_vs_lynhuang.md) §5 借鉴清单）
   - KafkaFake 单元测试
   - 6 个事件系统

2. **Kafka 特色线**（来自 [`开发文档_v0.1.md`](../开发文档_v0.1.md) §4 + §10 v0.2 路线图）
   - 多 Topic 路由（§4.1）
   - Key Routing 顺序保证（§4.3）
   - Header Trace / 透传增强（§4.9）

3. **推迟到 v0.3**（按 ROI 与依赖关系）
   - 时间轮延迟消息（§4.5）
   - DLQ 高级（trace 截断改进 + 多 DLQ）
   - 批量消费（§4.10）
   - Replay（§4.8）
   - 性能基准

| 项 | 决议 |

| 范围选择 | C 综合路线 |
| 实施节奏 | v0.2 走 5 步，v0.3 走剩余 5 步 |
| RFC 形式 | 先 RFC 0003 锁定范围，再按 Step 走 |
| 实施日志 | 沿用 v0.1 14 步风格（每 Step 一节） |

## 兼容性影响

### API 兼容性

| 影响 | 范围 | 处理 |
| --- | --- | --- |
| **KafkaFake** 新增 | 无（旧 API 行为不变） | 新增 `Kafka::fake()` + `assertXxx`，不破坏 v0.1 |
| **6 个事件** 新增 | 无 | 新增 `MessagePublishing` 等 6 个事件类，dispatch 行为是新增，**不**改 v0.1 行为 |
| **多 Topic 路由** 增强 | 向后兼容 | `KafkaConfig::resolveTopic($queue)` v0.1 已有 `topics` map 字段，v0.2 只是补全 fallback |
| **Key Routing** 新增 | 无 | 新增 `KafkaQueue::push($job, $data, $queue, $key)` 第 4 参数，旧代码不传照常工作 |
| **Header Trace 增强** | 向后兼容 | v0.1 `Header::TRACE_ID = 'x-trace-id'` 保留，v0.2 新增 `Header::TRACEPARENT = 'traceparent'`（W3C 格式），不破坏 |

### PHP 7.4 兼容约束

| 新增 | 依赖现代语法 | 处理 |
| --- | --- | --- |
| **事件类** | 用 readonly | 7.4 不支持。改用 `private` 字段 + getter（与 v0.1 风格一致） |
| **KafkaFake** | 暂无 | 与 v0.1 同构 |
| **Key Routing** | 暂无 | 已有 immutable + with 链式 |

### Laravel 8/9/10/11 兼容

| 新增 | 兼容性 |
| --- | --- |
| `QueueFake`（KafkaFake 借鉴） | 与 Laravel `Queue::fake()` 同构 |
| `Dispatchable` 事件 | Laravel 5.4+ 全部支持 |
| `W3C Trace Context` header | Kafka broker 0.11+ 全部支持（仅消费端读 header） |

### 数据库 / 性能

- v0.2 不改 `failed_jobs` 表结构
- 不引入新依赖
- 6 个事件 + KafkaFake 共增加约 5-10 个新类，每个类 50-200 行代码

## 替代方案

### v0.2 范围选择

| 方案 | 内容 | 评价 |
| --- | --- | --- |
| A 纯借鉴 | KafkaFake + 6 事件 + 借鉴生态 | 易测试，缺 Kafka 特色 |
| B 纯 Kafka 特色 | 7 个 Kafka 能力 | 强能力，缺测试基础设施 |
| **C 综合** | **借鉴 2 个 + 特色 3 个** | **平衡**（用户已选） |
| D 拆分 v0.2+v0.3 | v0.2 借鉴 2 个，v0.3 特色 5 个 | 但用户希望 v0.2 走部分特色 |

### KafkaFake 实现路径

| 路径 | 思路 | 评价 |
| --- | --- | --- |
| **复用 mateusjunges 模式** | `Kafka::fake()` 返回 fake manager，forwardCallTo 真实方法 | 简洁，但与 Laravel `Queue::fake()` 风格不同 |
| **对接 Laravel Queue Fake** | `Queue::fake()` 同时 fake Kafka driver | 与 Laravel 生态贴合，但 v0.1 没让 KafkaQueue 实现 `QueueFake` 钩子 |
| 独立 `Kafka::fake()` 静态调用 | 模仿 mateusjunges | 简单直接 |

**选择**：方案 1 + 方案 3 混合——`Kafka::fake()` 是主入口，但内部不 forwardCallTo 真实 manager，而是把所有 push 记录到 Fake 实例。

### 6 个事件 vs 4 个事件

| 方案 | 事件 | 评价 |
| --- | --- | --- |
| **6 个** | Publishing / Published / Consuming / Consumed / Failed / SentToDLQ | 覆盖全链路 |
| 4 个 | 合并 Publishing/Published 为 MessageLifecycle；合并 Consuming/Consumed 同 | 简化但丢失阶段信息 |
| 2 个 | 仅 MessageSent + MessageReceived | 太少，metrics/tracing 难做 |

**选择**：6 个。事件本身成本低（每个类 ~30 行），不增加复杂度。

### Header Trace 实现

| 方案 | 思路 | 评价 |
| --- | --- | --- |
| 自定义 x-trace-id | v0.1 已有 | 简单，但不能跨服务 |
| W3C Trace Context | 完整 traceparent / tracestate | 标准，但需要 v0.2 新增解析逻辑 |
| OpenTelemetry SDK | 完整方案 | 重型，v0.4 评估 |

**选择**：v0.2 保留 `x-trace-id`，新增 `traceparent` header（按 W3C 格式手动构造），不引入 OTel SDK。v0.4 评估 OTel 完整集成。

## 开放问题（v0.2 启动前）
