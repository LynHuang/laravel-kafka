## Step 1: 批量消费（2026-08-25）

### 目的

把 `Consumer::poll` 单条拉取扩展为 `pollBatch(int $max, int $timeoutMs)` 批量拉取，配合 `kafka:work --batch-size` 选项和 `commitBatch()` 整批 commit，提升吞吐。

### 产出文件

| 类型 | 文件 | 变更 |
| --- | --- | --- |
| 改 | `src/Consumer/Consumer.php` | 新增 `pollBatch(int $max, int $timeoutMs): array` + `commitBatch(): void` |
| 改 | `src/Console/WorkCommand.php` | 新增 `--batch-size=N` (默认 1) + `--batch-timeout=2000` (ms) 选项 + 主循环分支 |
| 新 | `tests/Unit/Consumer/ConsumerBatchTest.php` | 7 个 Mockery 单元测试 |

### 关键设计点

**4 重死循环防护**：
1. 拉够 `$max` 条 → `break`
2. 达到 `deadline` → `break`
3. **连续 2 次** `RD_KAFKA_RESP_ERR__TIMED_OUT` → 早返回
4. 达到 `maxIters = $max + 2` → `break`

**`commitBatch` 整批原子语义**：
- librdkafka 没有"按消息列表 commit" API，commit = "消费位置"
- 单条失败 → 不调 commitBatch → 整批下次重投
- v0.3 不支持部分 commit

**已知待办**：
- 毒消息问题：单条失败 → 整批重投 → 同一毒消息无限重试（v0.4 评估 dead-letter on N failures）
- per-partition 批量：当前混合返回，v0.4 评估

## Step 2: 时间轮分层延迟消息（2026-08-25）

### 目的

替换 v0.1/v0.2 的占位实现（`x-available-at` header + 同步阻塞），用"分层 topic"模拟时间轮：5s/30s/60s/300s/1800s/3600s/86400s 共 7 个 tier。

### 产出文件

| 类型 | 文件 | 变更 |
| --- | --- | --- |
| 新 | `src/Delay/DelayRouter.php` | 选最近一层 tier topic 的核心路由类 |
| 改 | `src/Queue/KafkaQueue.php` | `later()` 改用 `DelayRouter` 路由到 tier topic（保留 v0.2 行为 fallback） |
| 改 | `src/LaravelKafkaServiceProvider.php` | `DelayRouter` 单例绑定（从 `delay.tiers` / `delay.topic_prefix` 读配置） |
| 新 | `tests/Unit/Delay/DelayRouterTest.php` | 10 个单元测试 |

### 关键设计点

**`DelayRouter::route(int $delaySeconds)`**：
- 给定 delay 选**最近一层**（向上取整）
- delay=3s → 5s tier
- delay=10s → 30s tier
- delay=90000s → 86400s（最大 tier 兜底）
- 校验：tier 必须升序 + 全部 > 0

**`KafkaQueue::later` 新实现**：
```php
public function later($delay, $job, $data = '', $queue = null)
{
    $delaySeconds = max(1, (int) $delay);
    if ($this->container !== null && $this->container->bound(DelayRouter::class)) {
        $router = $this->container->make(DelayRouter::class);
        $route = $router->route($delaySeconds);
        return $this->pushRaw(
            $this->createPayload($job, $this->connectionName, $data, $queue),
            $route['topic'],  // 写到 tier topic
            ['delay_seconds' => $delaySeconds, 'delay_tier' => $route['tier'],
             'x-original-queue' => (string) ($queue ?? $this->config->defaultTopic())]
        );
    }
    // 回退 v0.2 行为（header 同步阻塞）
}
```

**已知待办**：
- `kafka:delay:work` worker 还没写（监听 tier topic + sleep tier + requeue）→ v0.4 评估
- 业务方需要自己建 tier topic（broker 启动时 + via AdminClient API）

## Step 3: DLQ 高级（2026-08-25）

### 目的

v0.1/v0.2 单一 DLQ topic 不足：不同异常需要不同处理（fatal → 人工 / transient → 自动重试 / validation → 调试）。v0.3 加 3 个增强：异常类路由、限速、`dlq:tail` 命令。

### 产出文件

| 类型 | 文件 | 变更 |
| --- | --- | --- |
| 新 | `src/Queue/Failed/ExceptionClassRouter.php` | 异常类名 → DLQ topic 路由（含 instanceof 继承匹配） |
| 新 | `src/Queue/Failed/DlqRateLimiter.php` | 每分钟 N 条限速（滑动窗口） |
| 新 | `src/Console/DlqTailCommand.php` | `php artisan kafka:dlq:tail <topic>` 实时打印（不 commit） |
| 改 | `src/LaravelKafkaServiceProvider.php` | 注册 DlqTailCommand |
| 新 | `tests/Unit/Queue/Failed/ExceptionClassRouterTest.php` | 7 个测试 |
| 新 | `tests/Unit/Queue/Failed/DlqRateLimiterTest.php` | 6 个测试 |

### 关键设计点

**`ExceptionClassRouter`**：
- 配置：`failed.dlq.topic_map`（`['App\Exception\BizFatal' => 'fatal-topic', ...]`）
- 匹配：`instanceof` 关系（子类也命中父类路由）
- 兜底：`failed.dlq.topic`（默认）→ 找不到匹配时

**`DlqRateLimiter`**：
- 简单内存计数器 + 60s 滑动窗口
- 多 worker 部署会**各自限速**（实际 100 × N），生产环境建议 Redis 共享（v0.4 评估）

**`kafka:dlq:tail`**：
- 独立 consumer group（`kafka-dlq-tail-<hostname>-<pid>`）→ 不影响主消费者
- 不 commit offset（运维可重跑）
- 打印关键 header（exception / original / attempts / failed_at）

**已知待办**：
- `HybridFailedJobHandler` / `DlqFailedJobHandler` **没**集成 `ExceptionClassRouter` / `DlqRateLimiter`（v0.3 MVP，框架就位但 handler 没接入）→ v0.3.1 评估
- AutoReplay 钩子（连续 N 次失败自动 requeue）→ v0.4 评估

## Step 4: Replay CLI（2026-08-25）

### 目的

业务方需要"重跑过去一段时间窗口的消息"（数据修复 / 重新触发下游）。`php artisan kafka:replay` 暴露这个能力。

### 产出文件

| 类型 | 文件 | 变更 |
| --- | --- | --- |
| 新 | `src/Replay/TimeWindowParser.php` | 解析 `-1h` / `now` / `1700000000` / `2026-08-25 10:00:00` 等格式 |
| 新 | `src/Replay/Replayer.php` | 窗口解析 + 参数校验（from < to） |
| 新 | `src/Console/ReplayCommand.php` | `php artisan kafka:replay --topic=X --from=-1h --to=now --target-topic=Y --group=replay-runner` |
| 改 | `src/LaravelKafkaServiceProvider.php` | 注册 ReplayCommand |
| 新 | `tests/Unit/Replay/TimeWindowParserTest.php` | 10 个测试 |
| 新 | `tests/Unit/Replay/ReplayerTest.php` | 4 个测试 |

### 关键设计点

**`TimeWindowParser`** 支持格式：
- `now` → 当前时间
- `-1h` / `-30m` / `-7d` / `-60s` → 相对时间
- `1700000000` → 绝对 timestamp
- `2026-08-25 10:00:00` → 绝对时间字符串（strtotime）

**`kafka:replay` 命令**：
- 4 个必填参数：`--topic` / `--from` / `--to` / `--target-topic`
- 独立 `--group`（默认 `replay-runner`，不污染主消费者）
- v0.3 MVP：**只做窗口校验**，实际 reproduce 留 v0.4 评估（需 `offsetsForTimes` + 遍历 partition + re-produce）

**已知待办**：
- 实际 `offsetsForTimes` 调 + 多 partition 遍历 → v0.3.1
- 保留 `original_*` headers 的 reproduce → v0.3.1
- dry-run 模式（只打印不实际 re-produce）→ v0.4 评估

## Step 5: 性能基准（2026-08-25）

### 目的

3 个独立 benchmark 脚本量化 laravel-kafka 的吞吐 / 延迟能力，给业务方 SLA 参考 + 后续优化提供 baseline。

### 产出文件

| 类型 | 文件 | 变更 |
| --- | --- | --- |
| 新 | `benchmarks/produce-throughput.php` | 单 producer 极限发送（参数：messages / payload-size / topic） |
| 新 | `benchmarks/consume-throughput.php` | 单 consumer 极限消费（参数：expected / topic / timeout） |
| 新 | `benchmarks/latency-p50-p99.php` | produce → consume 端到端延迟分布（p50/p90/p95/p99） |
| 新 | `benchmarks/README.md` | 用法 + 启动 Kafka + 跑分说明 + v0.3 实测基线参考 |

### 关键设计点

**3 个脚本独立运行**（不依赖 testbench / Laravel 容器），直接 `php script.php [args]`。

**输出维度**：
- Produce：msg/s + MB/s
- Consume：msg/s + 端到端延迟 p50/p95/p99
- Latency：p50/p90/p95/p99/min/max

**环境变量**：`KAFKA_BROKERS` 默认 `localhost:9092`。

**已知待办**：
- vs mateusjunges 对比脚本（`compare-mateusjunges.php`）→ v0.4 评估
- CI 跑分入库（每 PR 自动跑分）→ v0.4 评估
