### 16.1 Step 1 - KafkaFake 单元测试能力

**时间**：2026-08-25 15:55 ~ 16:30
**目的**：借鉴 mateusjunges 的 `Kafka::fake()` 模式，让业务方在单元测试中验证 Kafka 消息细节（topic / header / payload），无需真 Kafka 集群。

**RFC 引用**：RFC 0003 Step 1，决议 #1（`Kafka::fake()`）+ #2（事件命名 Message 前缀 v0.1 风格）

**产出文件**：

| 文件 | 大小 | 用途 |
| --- | --- | --- |
| `src/Support/Testing/FakeMessageStorage.php` | 1.9 KB | Fake 消息存储，记录所有 `pushRaw` 的 `['topic', 'message']` 二元组 |
| `src/Support/Testing/KafkaFake.php` | 3.5 KB | 断言门面：`assertPushed / assertPushedOn / assertPushedTimes / assertPushedOnTimes / assertNothingPushed` |
| `src/Manager/KafkaManager.php` | 改 ~10 行 | 加 `fake()` / `isFake()` 方法 |
| `src/Facades/Kafka.php` | 改 ~15 行 | 加 `Kafka::fake()` 静态方法 |
| `src/Queue/KafkaQueue.php` | 改 ~20 行 | `pushRaw` 增加 fake 分支 |
| `tests/Unit/Support/Testing/FakeMessageStorageTest.php` | 1.7 KB | 4 个测试用例 |
| `tests/Unit/Support/Testing/KafkaFakeTest.php` | 3.5 KB | 7 个测试用例 |
| `tests/Unit/Manager/KafkaManagerTest.php` | 1.3 KB | 4 个测试用例 |
| `tests/Unit/Queue/KafkaQueueFakeTest.php` | 3.1 KB | 4 个测试用例 |

**关键设计点**：

1. **fake 链路 3 段式**：
   ```
   Kafka::fake()
     ├─ new FakeMessageStorage（singleton via container）
     ├─ manager.fake()                       // 设标志
     └─ return new KafkaFake($storage)
   ```
   业务方拿到 `KafkaFake` 实例做断言。

2. **fake 注入点选在 `KafkaQueue::pushRaw`** 而非 `Producer::send`：
   - 原因：`pushRaw` 已经在 `KafkaQueue` 这一层，能拿到 `$topic`（用 `KafkaConfig::resolveTopic` 解析过）+ 构造好的 `Message`
   - 优势：业务方既验证 Kafka 层面细节（topic / header / payload），又保持 Queue 驱动语义
   - 对比 mateusjunges：他们 fake 在 `Producer` 层，只记录 `ProducerMessage`，拿不到 topic

3. **`FakeMessageStorage` 是 plain data class**：
   - 不用 singleton，**通过容器 instance() 单例化**——一个测试一个 storage
   - 4 个方法：`record / all / count / isEmpty / flush`
   - 业务方可以手动 `flush()` 在测试 setUp 里清空（避免污染）

4. **`KafkaFake` 5 个断言方法**（区别于 mateusjunges 的命名）：
   | 我们的 | mateusjunges | 含义 |
   | --- | --- | --- |
   | `assertPushed($topic, $cb)` | `assertPublished` | 至少 1 条匹配 |
   | `assertPushedOn($topic, $cb)` | `assertPublishedOn` | 在指定 topic 至少 1 条 |
   | `assertPushedTimes($times, $topic, $cb)` | `assertPublishedTimes` | 恰好 N 条 |
   | `assertPushedOnTimes($topic, $times, $cb)` | `assertPublishedOnTimes` | 在指定 topic 恰好 N 条 |
   | `assertNothingPushed()` | `assertNothingPublished` | 没有 |
   - 命名差异：因为我们是 Queue 驱动，"published" 不如 "pushed" 准确

5. **PHPUnit `Assert::xxx` 而非自定义 AssertionFailedError**：
   - 用 `PHPUnit\Framework\Assert as PHPUnit` 别名简化
   - 失败时 PHPUnit 自动捕获 `AssertionFailedError`，业务方测试报告友好

**关键认知**：

1. **`Kafka::fake()` 在生产代码里是无操作**：fake 模式只影响 `pushRaw` 走 fake 分支，`Producer::send` 仍然可用
2. **fake 是单 manager 单例**：业务方开多个测试用 `Kafka::fake()` 不会冲突（singleton 但 fake 标志会多次设 true）
3. **fake 模式 + 真发模式不混**：要么全 fake（`manager.fake()`），要么全真发（默认）

**已知待办**：

- ⚠️ **未实际跑过 `vendor/bin/phpunit`**：与 v0.1 一样，Windows 工作区可能没 PHP + ext-rdkafka，CI 兜底
- 📌 **不支持 fake `pop()`**：v0.2 只 fake `pushRaw`，不 fake consume 路径（mateusjunges 也不 fake consume）—— 单测"被消费"用 `Queue::fake()` 或 `Bus::fake()` 走 Laravel 路径
- 📌 **fake 模式不能 unset**：一旦 `fake()`，manager 标志位就是 true，要回真发只能 `disconnect()` 重建 manager（v0.3 评估 `unfake()` API）
- 📌 **断言 callback 必须返回 `bool`**：返回 `true` 算匹配，`false` 算不匹配，返回其他类型会被隐式转 bool，**可能**踩坑

### 16.2 Step 2 - 6 个事件系统

**时间**：2026-08-25 16:10
**目的**：让业务方在 Laravel Event 体系下订阅 Kafka 全链路事件（生产 / 消费 / 失败 / DLQ）。
**RFC 引用**：决议 #2（`Message` 前缀）+ 借鉴 mateusjunges 的 6 事件。

**产出文件**：

| 文件 | 大小 | 用途 |
| --- | --- | --- |
| `src/Events/MessagePublishing.php` | 0.8 KB | push 之前 |
| `src/Events/MessagePublished.php` | 0.6 KB | push 之后（broker ack） |
| `src/Events/MessageConsuming.php` | 0.6 KB | consume 之前 |
| `src/Events/MessageConsumed.php` | 0.6 KB | 业务处理成功 |
| `src/Events/MessageFailed.php` | 0.7 KB | 业务异常 |
| `src/Events/MessageSentToDLQ.php` | 0.7 KB | DLQ 写入 |
| `src/Queue/KafkaQueue.php` | 改 | pushRaw dispatch 2 事件 |
| `src/Consumer/Handler/NativeHandler.php` | 改 | handle dispatch 3 事件 |
| `src/Queue/Failed/DlqFailedJobHandler.php` | 改 | handle dispatch 1 事件 |
| `tests/Unit/Events/EventTest.php` | 3.0 KB | 7 用例（6 事件 + final 反射） |

**关键设计点**：

1. **命名：v0.1 风格**（`Message` 前缀）：
   - `MessagePublishing` / `MessagePublished` / `MessageConsuming` / `MessageConsumed` / `MessageFailed` / `MessageSentToDLQ`
   - mateusjunges 用 `PublishingMessage`（动词在前），但我们用名词在前更符合 Laravel 事件命名习惯

2. **值对象 + 命名访问器**（与 v0.1 `Message` 一致）：
   - `private` 字段 + 命名访问器（`topic()` / `message()` / `error()`）
   - 不暴露 setter，事件创建后不可变

3. **dispatch 位置设计**：
   - `KafkaQueue::pushRaw` 真发路径上 dispatch 2 个（`Publishing` → send → `Published`）
   - **fake 模式下不 dispatch 事件**
   - `NativeHandler::handle` dispatch 3 个（`Consuming` → Worker::process → `Consumed` 或 `Failed`）
   - `DlqFailedJobHandler::handle` 在 producer.send 成功后 dispatch 1 个（`SentToDLQ`）

4. **容器防御**：
   - `dispatchEvent()` 检查容器是否绑定 `Dispatcher` 才 dispatch
   - 缺绑定时静默跳过（不抛异常）

**已知待办**：

- 📌 事件没在 fake 模式下 dispatch（业务方测事件得用真发）
- 📌 `MessageFailed` 在 fail handler 之前 dispatch
- 📌 v0.2 不区分 sync/async 事件

### 16.3 Step 3 - 多 Topic 路由

**时间**：2026-08-25 16:15
**目的**：业务方按业务线（订单 / 邮件 / 报表）把消息推到不同 topic，无需关心物理 topic 名。
**RFC 引用**：决议 #3（v0.2 不支持正则匹配）

**产出文件**：

| 文件 | 性质 | 内容 |
| --- | --- | --- |
| `src/Queue/KafkaQueue.php` | 改 | `pushRaw` 加 `options['topic']` 显式覆盖；新增 `resolveTopicWithOptions` 私有方法 |
| `src/Queue/KafkaQueue.php` | 改 | `push($job, $data, $queue, ?string $key)` 第 4 参数 |
| `tests/Unit/Queue/KafkaQueueOptionsTest.php` | 改 | 加 4 个 multi-topic 用例 + 3 个 trace 用例 |

**关键设计点**：

1. **v0.1 已有 `KafkaConfig::resolveTopic`**——Step 3 主要是补 `options['topic']` 显式覆盖
2. **解析优先级**：
   ```
   options['topic']  (最优先)
     ↓ 空
   KafkaConfig::topics[$queue]  (映射)
     ↓ 无映射
   $queue  (同名)
     ↓ 空
   $defaultTopic
   ```
3. **业务方使用方式**：
   ```php
   // 方式 1：config 映射（推荐）
   // config/kafka.php
   'topics' => ['emails' => 'app.emails'],
   Queue::push(new SendEmail($user), '', 'emails');  // → topic: app.emails

   // 方式 2：显式 topic
   $queue->pushRaw($payload, 'emails', ['topic' => 'app.emails.urgent']);
   ```

**已知待办**：

- ⚠️ topic 不存在时不会自动创建
- 📌 正则匹配推迟到 v0.4

### 16.4 Step 4 - Key Routing 顺序保证

**时间**：2026-08-25 16:18
**目的**：让业务方按 key 路由消息到固定 partition，实现同 key 严格顺序（订单按 user_id 分区）。
**RFC 引用**：决议 #4（默认 `null`）

**产出文件**：

| 文件 | 性质 | 内容 |
| --- | --- | --- |
| `src/Queue/KafkaQueue.php` | 改 | `push($job, $data, $queue, ?string $key)` 第 4 参数（已含在 Step 3 改动） |
| `tests/Unit/Queue/KafkaQueueOptionsTest.php` | 改 | 4 个 Key Routing 用例 |

**关键设计点**：

1. **`KafkaQueue::push` 加第 4 参数**（向后兼容）：
   - v0.1：`push($job, $data = '', $queue = null)`
   - v0.2：`push($job, $data = '', $queue = null, ?string $key = null)`

2. **partition 路由规则**（librdkafka）：
   - `key !== null` → 用 murmur2(key) 算 partition → 同 key 永远同 partition
   - `key === null` → 轮询 partition

**业务方使用方式**：
```php
// 同一 user 的订单严格顺序
Queue::push(new ProcessOrder($order), '', 'orders', (string) $order->user_id);
```

**已知待办**：

- 📌 `KafkaQueue::push` 第 4 参数是非标 Laravel 接口
- 📌 重试消息按 `x-attempt` 还是 `x-original-key` 路由？v0.3 评估

### 16.5 Step 5 - Header Trace / 透传增强

**时间**：2026-08-25 16:25
**目的**：让 Kafka 消息携带 W3C Trace Context（traceparent），跨服务追踪标准；保留 v0.1 `x-trace-id` 16 字符 header 兼容。
**RFC 引用**：决议 #5（traceparent 优先，旧消息回退）

**产出文件**：

| 文件 | 性质 | 内容 |
| --- | --- | --- |
| `src/Support/Header.php` | 改 | 新增 `TRACEPARENT` / `TRACESTATE` 常量 |
| `src/Support/TraceContext.php` | 重写 | W3C 标准生成 / 解析 / child / shortTraceId |
| `src/Queue/KafkaQueue.php` | 改 | `buildMessage` 写 traceparent + x-trace-id |
| `src/Consumer/Consumer.php` | 改 | `wrap` 读 traceparent + 旧消息回退 |
| `tests/Unit/Support/TraceContextTest.php` | 重写 | 7 用例覆盖 W3C 格式 |
| `tests/Unit/Queue/KafkaQueueOptionsTest.php` | 改 | 3 个 trace 写入测试 |

**关键设计点**：

1. **W3C Trace Context 格式**：
   ```
   traceparent: 00-<32hex trace-id>-<16hex parent-id>-<2hex flags>
   example:    00-0af7651916cd43dd8448eb211c80319c-b7ad6b7169203331-01
   ```

2. **双 header 兼容**：
   - `traceparent` 完整 W3C（v0.2 新）
   - `x-trace-id` 前 16 hex（v0.1 旧）
   - **不冲突**：trace-id 前 16 hex = x-trace-id

3. **Consumer::wrap 旧消息回退**：
   ```php
   if (!isset($headers[TRACEPARENT]) && isset($headers[TRACE_ID])) {
       $shortId = $headers[TRACE_ID];
       $headers[TRACEPARENT] = '00-' . str_pad($shortId, 32, '0', STR_PAD_LEFT) . '-' . randomBytes(8) . '-01';
   }
   ```

4. **`TraceContext::child($parentTraceparent)`**：
   - 保留 trace-id（同调用链）
   - 生成新 parent-id（区分处理阶段）

5. **`KafkaQueue::buildMessage` 接受 `options['traceparent']`**：
   - 默认调 `TraceContext::next()` 生成新
   - 业务方传 `options['traceparent' => $parentTp]` 时透传

**已知待办**：

- 📌 `tracestate` 头 v0.2 写但不读
- 📌 `flags=01` 硬编码全采样
- 📌 W3C Trace Context spec 是 Level 1（最新版 Level 2 2024）
