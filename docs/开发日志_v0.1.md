**目的**：建立 Composer 包的基础元数据与开发工具配置，使仓库可被 `composer install` 识别、可被 IDE 索引、可被 CI 拉取。

**产出文件**：

| 文件 | 大小 | 用途 |
| --- | --- | --- |
| `composer.json` | 2.0 KB | 包元数据、依赖、autoload、scripts、laravel 包发现 |
| `LICENSE` | 1.1 KB | MIT 协议，Copyright (c) 2026 Lyn-Huang |
| `README.md` | 4.5 KB | 快速开始、特性矩阵、对比表、FAQ、路线图、License |

| `.editorconfig` | 0.3 KB | 统一缩进 4 空格、LF、UTF-8 |

| `.php-cs-fixer.php` | 2.0 KB | PER 2.0 风格、严格类型、排序 import、4 空格 |
| `phpstan.neon` | 0.3 KB | level 6、仅扫 src/、忽略 ext-rdkafka 反射错误 |

**关键设计点**：

1. **`composer.json` 依赖版本跨度**：
   - `illuminate/queue: ^8.0 || ^9.0 || ^10.0 || ^11.0`
   - `nesbot/carbon: ^2.0 || ^3.0`（Composer 会按 PHP 版本自动选 Carbon 2 for PHP 7.4）
   - `phpunit/phpunit: ^9.0 || ^10.0`（不引入 11，因 11 要 PHP 8.2+）
   - `orchestra/testbench: ^6.0 || ^7.0 || ^8.0 || ^9.0`（与 Laravel 主版本同步）
   - `minimum-stability: stable` + `prefer-stable: true`：避免 Carbon 3 alpha 锁死

2. **`.gitattributes` export 排除**：打包成 dist tarball 时排除 CI/开发/测试文件，只把 src/、config/、composer.json、LICENSE 带走。

3. **`.php-cs-fixer.php` 规则选择**：
   - `@PER` 而非 `@PSR12`：PER 是 PSR-12 的现代化升级版，更符合 Laravel 风格
   - `single_quote`、`array_syntax: short`、`declare_strict_types: true`：硬性约束
   - `ordered_class_elements`：与 §13.3 类属性顺序约束一致

4. **`phpstan.neon` level 6**：v0.1 不追求 8/9，留出 7.4 兼容灵活度（README 提了 level 6）。

5. **`extra.laravel.providers` 与 `extra.laravel.aliases`**：Laravel 5.5+ 包发现机制自动注册 `LaravelKafkaServiceProvider` 与 `Kafka` Facade。

**已知待办**：

- ⚠️ `composer.json` 中 `ext-rdkafka: *` 在 Windows + 无 rdkafka 扩展环境下 `composer install` 会失败。下次提交需在 README §系统要求 强调 PECL 安装命令。
- ⚠️ `extra.laravel.aliases.Kafka` 与 KafkaJS 等生态有命名冲突风险，但不影响包发现，仅在用户主动 `use Kafka;` 时报错，留到 v0.2 评估。
- 📌 当前 `composer.json` 还在本地工作区，**未实际跑过 `composer validate`**，需 Step 11 之后做一次本地校验（Windows 环境可能无 PHP，跳过则用 GitHub Actions 兜底）。

### 16.2 Step 2 - 源码核心层

**时间**：2026-08-20 14:02
**目的**：实现包的心脏——配置值对象、Manager、Factory、ServiceProvider。

**产出文件**：

| 文件 | 大小 | 用途 |
| --- | --- | --- |
| `src/Config/KafkaConfig.php` | 8.7 KB | 不可变配置值对象，封装所有 Kafka 客户端配置 |
| `src/Manager/KafkaManager.php` | 2.7 KB | 多 connection 管理、单例缓存、default 解析 |
| `src/Manager/ConnectionFactory.php` | 1.5 KB | 根据 `KafkaConfig` 构造 `KafkaQueue` |
| `src/LaravelKafkaServiceProvider.php` | 4.9 KB | 注册入口、queue 扩展、failer、命令、配置发布 |

**关键设计点**：

1. **`KafkaConfig` 不可变值对象**：
   - 全部字段 `private` + 命名访问器（`name()` / `brokers()` / ...），不允许外部改
   - 构造时做最小校验：brokers 非空、defaultTopic 非空、protocol ∈ 4 种之一
   - `resolveTopic(?string $queue)` 实现 §3.3 队列名映射逻辑
   - `toProducerRdKafkaConfig()` / `toConsumerRdKafkaConfig()` 把内部结构化配置翻译成 librdkafka 字符串键值对
   - SSL/SASL 仅在对应 protocol 下注入字段，避免 librdkafka 报"未知配置"

2. **`KafkaManager` 缓存策略**：
   - `connections` 数组按 name 缓存 `KafkaQueue` 实例
   - `configs` 数组按 name 缓存 `KafkaConfig` 实例
   - `disconnect()` 留给 Octane / 长连接场景（v0.4 接入）
   - `registerConnections()` 由 ServiceProvider 启动时一次性塞入

3. **`ConnectionFactory` 装配模式**：
   - 三个子 Factory（Producer / Consumer / FailedHandler）由容器注入
   - 单方法 `make(KafkaConfig, string $connectionName): KafkaQueue`
   - 装配过程与连接管理解耦：以后想加缓存、加多 producer 路由都不动 Manager

4. **`ServiceProvider` 启动顺序严格把控**：
   - `register()`：merge 配置、绑定单例、扩展 queue connector
   - `boot()`：注册 failer、JobFailed 事件、命令、配置发布
   - **关键**：`Queue::extend('kafka', ...)` 必须在 `register()` 里而不是 `boot()`，因为 `config('queue.connections.kafka')` 的解析依赖 connector 已注册
   - `queue.failer.kafka` 仅在 `database` / `hybrid` 模式注册，`dlq` 模式跳过

5. **`JobFailed` 事件占位**：
   - v0.1 的失败处理由 `KafkaJob::fail()` 直接调用 handler
   - 事件监听器留空 handler，留给 v0.2 接入告警 / 监控钩子

**已知待办**：

- ⚠️ `KafkaConfig::fromArray` 强依赖 `config('kafka.connections.default.*')` 结构，发布前要补全单元测试覆盖所有字段映射
- ⚠️ `KafkaManager::getDefaultConnection()` 用 `function_exists('config')` 做兜底，这只是给非 Laravel 场景（如纯单元测试 mock）的逃生口，正常调用一定走 Laravel 容器
- 📌 `LaravelKafkaServiceProvider::registerFailedHandlerEvent` 当前只占位，v0.1 真正失败逻辑在 `KafkaJob::fail()`；这个监听器是 v0.2+ 增强点
- 📌 `WorkCommand` 在 Step 2 还没产出，ServiceProvider 引用了但还没实现，会导致 autoloader 报 Class not found。**Step 7 必须先产出 WorkCommand 再回到本节验证。**

### 16.3 Step 3 - Producer 子系统

**时间**：2026-08-20 14:08
**目的**：实现向 Kafka 写消息的核心能力，包含消息值对象、序列化器、生产者、生产者工厂。

**产出文件**：

| 文件 | 大小 | 用途 |
| --- | --- | --- |
| `src/Producer/Message.php` | 2.3 KB | 不可变消息值对象（payload / headers / key / partition / timestampMs） |
| `src/Producer/Serializer/Serializer.php` | 0.7 KB | 序列化器接口（encode/decode/name） |
| `src/Producer/Serializer/PhpSerializer.php` | 1.4 KB | PHP serialize 实现，与 Laravel Job payload 兼容 |
| `src/Producer/Serializer/JsonSerializer.php` | 1.9 KB | JSON 实现，v0.2 启用（跨语言消费场景） |
| `src/Producer/Producer.php` | 4.8 KB | 封装 RdKafka\Producer，同步 produce + delivery 回调 |
| `src/Producer/ProducerFactory.php` | 2.2 KB | 构造 Conf、缓存 Producer、flushAll 钩子 |

**关键设计点**：

1. **`Message` 不可变 + 链式 with**：
   - `withHeaders()` / `withHeader()` / `withKey()` 复制出新实例，避免上游修改已构造的消息
   - 不在值对象层做序列化，序列化由 `Serializer` 接口负责，保持职责单一

2. **`Serializer` 接口三方法**：
   - `encode(mixed): string`
   - `decode(string): mixed`
   - `name(): string` —— 用于写入 Header（`x-serializer: php` / `x-serializer: json`），消费端按相同 name 解码
   - 所有方法失败抛 `SerializationException`，**不**直接抛 librdkafka / PHP 内置异常

3. **`PhpSerializer` 与 Laravel 兼容**：
   - `unserialize($raw, ['allowed_classes' => true])` 允许反序列化任何类（与 Laravel 默认一致）
   - 解码空字符串返回 `null`
   - 区分 `b:0;`（合法的 `false`）和 `unserialize` 返回 `false` 的失败情况

4. **`JsonSerializer` v0.2 启用**：
   - `JSON_UNESCAPED_UNICODE | JSON_UNESCAPED_SLASHES`：保留中文、保留 URL 斜杠
   - depth 512：足够深，PHP 7.4 默认 512
   - 解析 null 时区分 `'null'` 字符串和真正的 `null` 返回

5. **`Producer::send` 同步等待 delivery report**：
   - 用 `producev()`（带 headers / timestamp / opaque 的完整版本）+ `setDrMsgCb` 回调
   - 同步轮询 5s 直到 delivery 报告到来，避免业务层"以为发出去了但没到"
   - `random_int(0, PHP_INT_MAX)` 当 token 标识当前消息，回调里通过 `opaque` 找回
   - 失败时 `error_log` 记录到 PHP 错误日志，**不**直接抛异常（避免回调里抛异常）

6. **`Producer::fromConf(Conf)` 静态构造**：
   - 在 Factory 里 `new Producer(new RdKafkaProducer($conf))` 再绑 `setDrMsgCb`
   - 这是因为回调闭包需要 `$instance` 引用，必须在 `new` 之后绑定
   - 去掉了原设计的循环引用 `fromConf($conf, $self)` 参数

7. **`ProducerFactory` 单例缓存**：
   - `instances[$config->name()]` 缓存已构造的 Producer
   - `flushAll()` 提供给 Worker 退出前批量 flush 的钩子
   - `setErrorCb` / `setLogCb` 仅记录到 PHP 错误日志；v0.2+ 接入 Laravel Log

**已知待办**：

- ⚠️ `Producer::send` 的 5s 同步等待是硬编码，应在 v0.2 改为 `kafka.send_timeout_ms` 配置项
- ⚠️ `Producer::send` 当前按"一条一条同步等"的语义，吞吐受限。v0.2 批量发送模式（`linger_ms` + `producev` + 批量 poll）需重写 send 路径
- 📌 `JsonSerializer` 暂未在 ServiceProvider 注册（默认走 PhpSerializer），Step 9 Facade 完成后接入
- 📌 `ProducerFactory` 的 `instances` 缓存没有 size 限制——但 Kafka 连接数本来就少，泄漏风险低
- 📌 `error_log` 输出在生产环境会被收集到 stderr；v0.2 应改成注入 `Psr\Log\LoggerInterface`

### 16.4 Step 4 - Consumer 子系统

**时间**：2026-08-20 14:15
**目的**：实现从 Kafka 拉消息的能力，含订阅描述、handler 路由、消费者、消费者工厂。

**产出文件**：

| 文件 | 大小 | 用途 |
| --- | --- | --- |
| `src/Consumer/Subscription.php` | 0.9 KB | 订阅描述（topic 列表） |
| `src/Consumer/Handler/HandlerInterface.php` | 0.5 KB | 消息处理器接口 |
| `src/Consumer/Handler/HandlerResult.php` | 1.7 KB | 三种结果：ack / requeue / dlq |
| `src/Consumer/Handler/HandlerResolver.php` | 0.8 KB | 决定消息交给哪个 handler（v0.1 统一走 NativeHandler） |
| `src/Consumer/Handler/NativeHandler.php` | 5.6 KB | Laravel Job 处理入口，调 Worker::process |
| `src/Consumer/Consumer.php` | 3.4 KB | 封装 RdKafka\KafkaConsumer，poll/ack/close |
| `src/Consumer/ConsumerFactory.php` | 2.5 KB | 构造 Conf、rebalance 回调、缓存 Consumer |

**关键设计点**：

1. **`Subscription` 简单值对象**：
   - 只持有 topic 列表，构造时校验至少 1 个 topic
   - v0.3 扩展：支持 per-topic handler、自定义选项

2. **`HandlerResult` 三态枚举（用类常量模拟）**：
   - 因为 PHP 7.4 没有 enum，用 `public const ACTION_* = '...'` + `in_array` 校验
   - `ack()` / `requeue()` / `dlq()` 三个静态工厂方法
   - `error()` 携带异常对象，下游 failedHandler 用来写 DLQ 上下文

3. **`HandlerResolver` v0.1 单路、v0.3 多路**：
   - v0.1：所有消息都返回 `NativeHandler` 单例
   - v0.3：根据 `Message::header('x-handler')` 路由到不同 handler（已留接口位）

4. **`NativeHandler` 是 Worker 桥**：
   - 从 `Message` 构造伪 `RdKafka\Message` 喂给 `KafkaJob`（Step 5 产出）
   - 调 `Illuminate\Queue\Worker::process($connectionName, $job, $options)`
   - **关键决策**：成功路径完全靠 Laravel `Worker::process` 内部逻辑，**不**重写
   - 异常路径：判断 `failed.driver` 决定是 ACK（database 模式让 Laravel 走默认）还是 DLQ/requeue（dlq/hybrid 模式）
   - 致命异常列表走 `kafka.connections.default.failed.hybrid.fatal_exceptions` 配置

5. **`Consumer::poll` 三态**：
   - `RD_KAFKA_RESP_ERR_NO_ERROR`：返回包装好的 `Message`
   - `PARTITION_EOF` / `TIMED_OUT`：返回 `null`（让 Worker 继续循环）
   - 其他错误：抛 `KafkaException`

6. **`Consumer::wrap` 注入 3 个 Kafka 侧 header**：
   - `x-original-topic` / `x-original-partition` / `x-original-offset`
   - 失败时这些 header 一并写入 DLQ 消息，定位原始位置

7. **`ConsumerFactory` rebalance 回调**：
   - `setRebalanceCb` 是 librdkafka 必须实现的：assign / revoke 时手动调用 `assign()`
   - 当前只记录到 `error_log`，v0.2 接入 Laravel 事件（`kafka.rebalance.assigned` / `kafka.rebalance.revoked`）

**已知待办**：

- ⚠️ `NativeHandler::createJob` 里构造的 `RdKafka\Message` 是为了 KafkaJob 拿到原始 partition/offset 字段。但 librdkafka `Message` 的 `headers` 是只读属性，**直接赋值在某些版本会失败**。Step 5 产出 KafkaJob 时需确认是否需要换构造签名（接受 `array $headers` 而不是 `RdKafka\Message`）。
- ⚠️ `Worker::process` 内部会触发 `JobFailed` 事件（已在 ServiceProvider 注册占位），事件里的 `$event->job` 实际是 `KafkaJob`。这要求 KafkaJob 必须能被识别——Step 5 必须确保。
- 📌 `ConsumerFactory::make($config, $subscription = null)` 第二个参数可选，但 KafkaManager 走的是 `make($config)` 单参路径。WorkCommand 里显式传 Subscription 是 v0.1 的预期用法。
- 📌 `error_log` 在生产环境会被收集到 stderr；v0.2 应改成注入 `Psr\Log\LoggerInterface`

### 16.5 Step 5 - Queue 子系统

**时间**：2026-08-20 14:20
**目的**：实现与 Laravel Queue 框架对接的三个核心类：Connector、Queue、Job。

**产出文件**：

| 文件 | 大小 | 用途 |
| --- | --- | --- |
| `src/Queue/KafkaConnector.php` | 1.3 KB | 实现 `ConnectorInterface`，从 Manager 拿 KafkaQueue |
| `src/Queue/KafkaQueue.php` | 4.3 KB | 继承 `Illuminate\Queue\Queue`，实现 push/pushRaw/later/pop |
| `src/Queue/KafkaJob.php` | 4.4 KB | 继承 `Illuminate\Queue\Jobs\Job`，包装 RdKafka\Message |

**关键设计点**：

1. **`KafkaConnector` 单职责**：
   - 只做 `connect(array $config): KafkaQueue` 一件事
   - 校验返回类型是 `KafkaQueue`，避免 `KafkaManager::connection()` 返回错误时上层不感知

2. **`KafkaQueue` 继承 `Illuminate\Queue\Queue`**：
   - **关键**：`parent::__construct(null)` —— 父类期望 `Container`，但 KafkaQueue 构造时容器可能还没准备好；用 `setContainer()` 延迟注入
   - 复用 `createPayload($job, $conn, $data, $queue)` 基类方法：自动序列化 Laravel Job + 注入 `displayName` / `data` / `job` 字段
   - 实现 `size()` 返回 0：v0.1 不接 Kafka admin API，v0.2 用 `getOffsetPositions` 估算 lag
   - 实现 `pop()` 返回 null：v0.1 设计是"必须通过 `kafka:work` 长进程消费"，不让 Laravel 自动 worker 拉

3. **`buildMessage` 注入 5 个基础 header**：
   - `x-trace-id`：用 `random_bytes(8)` 生成 16 字符十六进制（不依赖 ramsey/uuid 在生产路径上）
   - `x-queue` / `x-connection`：消费端还原队列名
   - `x-enqueued-at` / `x-retry-count`：retry 判定
   - `x-serializer: php`：消费端按相同规则解码
   - 延迟消息注入 `x-available-at`，由 NativeHandler 在消费时检查（v0.1 同步阻塞；v0.2 走时间轮）

4. **`KafkaJob` 继承 `Illuminate\Queue\Jobs\Job`**：
   - 父类构造签名为 `(Container, $connectionName, $queue, $rawBody)`，我们额外持有 `Consumer` 和 `RdKafka\Message`
   - `getJobId()`：优先 Header 注入的 `x-job-id`（push 时产生），否则用 offset
   - `attempts()` 返回 `retry_count + 1`：与 Laravel 语义一致（首次 = 1）
   - `delete()` 调父类 + `consumer->ack($rdMessage)`：commit offset
   - `fail($exception)`：调 `FailedJobHandlerFactory` 拿 handler，分发失败事件，再 ack offset

5. **`markAsFailed()` 用反射**：
   - Laravel 父类的 `$failed` 是 `protected`，PHP 7.4 没有"外部访问 protected 父类属性"语法
   - 用 `ReflectionClass::getProperty` + `setAccessible(true)` 强行写标志
   - 兼容性兜底：`hasProperty` 失败时静默跳过

6. **设计取舍：Header 用常量字符串而不是 enum**：
   - `Header::TRACE_ID` 等常量定义在 Step 8 的 `Support/Header.php`
   - 当前文件 forward reference 了这些常量，编译期不报错，运行时 `Header.php` 加载后即可
   - 好处：v0.1 还能用 IDE 跳转

**已知待办**：

- ⚠️ **依赖反向**：Step 5 引用了 Step 6 的 `FailedJobHandlerFactory` / `FailedJobHandlerInterface` / `FailedContext`，以及 Step 8 的 `Header`。**当前 PHP 文件会因 Class not found 而无法被 Composer 加载**。Step 6 / Step 8 必须紧接着产出，否则整个包不可运行。
- ⚠️ `KafkaQueue::setContainer` 是 `Illuminate\Contracts\Queue\Queue` 接口里没有的方法，但 Laravel 内部会通过属性赋值注入。v0.1 用显式方法更清晰，v0.2 评估要不要改用 `Queue::setContainer($app)` 兼容调用。
- ⚠️ `KafkaJob::fail()` 用了反射写 `failed` 标志，这是**侵入性**操作。Laravel 8/9/10/11 父类签名有差异时可能崩，需要 Step 11 单元测试覆盖。
- 📌 `KafkaQueue::size()` 返回 0 是 v0.1 妥协；用户用 `php artisan queue:size` 会一直看到 0，README 要加 FAQ 说明
- 📌 `KafkaQueue::pop()` 返回 null 意味着 `php artisan queue:work --once` 这种 Laravel 默认单次消费命令在 Kafka 驱动上**不工作**，必须用 `php artisan kafka:work`（Step 7 产出）

### 16.6 Step 6 - Failed 子系统

**时间**：2026-08-20 14:28
**目的**：实现三种失败处理模式（database / dlq / hybrid），这是 §3.6 三模式设计的落地。

**产出文件**：

| 文件 | 大小 | 用途 |
| --- | --- | --- |
| `src/Queue/Failed/FailedJobHandlerInterface.php` | 0.6 KB | Handler 接口（`handle(KafkaJob, Throwable, FailedContext): void`） |
| `src/Queue/Failed/FailedContext.php` | 1.3 KB | 失败上下文值对象（payload/headers/topic/partition/attempts） |
| `src/Queue/Failed/FailedJobHandlerFactory.php` | 3.8 KB | 工厂，按 `failed.driver` 路由到 3 种实现 |

| `src/Queue/Failed/DlqFailedJobHandler.php` | 2.8 KB | 写 DLQ topic，注入 9 个 DLQ 专属 header |

**关键设计点**：

1. **`FailedContext` 打包元信息**：
   - 避免 `handle(KafkaJob, Throwable, string $topic, int $partition, ...)` 签名爆炸
   - 单一上下文值对象传递所有失败时需要的元信息

2. **`FailedJobHandlerFactory` 缓存 + 路由**：
   - `instances[$config->name()]` 缓存已构造的 handler（避免每次 fail 都 new 一遍）
   - `switch ($driver)` 路由 `database` / `dlq` / `hybrid` 三种实现
   - **关键**：DLQ topic 自动拼接 `$defaultTopic . $dlq.auto_topic_suffix`（用户可在 `failed.dlq.topic` 显式覆盖）

3. **`DatabaseFailedJobHandler` 复刻 Laravel schema**：
   - 表字段：`id` / `uuid` / `connection` / `queue` / `payload` / `exception` / `failed_at`
   - `payload` 用 `json_encode` 而不是 `base64_encode(serialize)`：与 Laravel 8+ 内部 `DatabaseUuidFailedJobProvider` 一致
   - `exception` 用 `\n` 拼接 class + message + trace（与 Laravel 一致）
   - `uuid` 用 `Ramsey\Uuid\UuidInterface` 生成

4. **`DlqFailedJobHandler` payload 不重新序列化**：
   - **关键**：DLQ 消息的 payload = 原消息的 payload，**不**重做 serialize
   - 原因：消费 DLQ 的人可能不是 PHP，原始 payload 字节对他们更有意义
   - 9 个 DLQ 专属 header 见 §3.6.3 设计
   - `x-original-headers` 是原 headers 的 JSON 序列化（让消费端能完整还原上下文）
   - `message` / `trace` 按配置项截断（默认 4KB / 32KB），避免 header 太大

5. **`HybridFailedJobHandler` 决策树实现**：
   - `isFatal` 检查异常类是否在 `fatal_exceptions` 列表（用户可配）
   - `attemptNumber = attempts() + 1` 1-indexed（首次失败 = 1）
   - `overLimit` 即 `attemptNumber >= maxAttempts`
   - **关键**：双写路径（database + DLQ）任一失败不应阻止另一个——try/catch 隔离
   - 真正的"仅 retry"路径**不**经过本 handler（由 `NativeHandler` 通过 `HandlerResult::requeue` 决策），所以这里只关心"已经决定要写失败"

6. **DLQ topic 自动拼接规则**：
   - 用户配置 `kafka.connections.default.failed.dlq.topic` 非空 → 用它
   - 否则用 `defaultTopic + auto_topic_suffix`（默认 `.dlq`）
   - 示例：默认 topic `laravel-jobs` → DLQ `laravel-jobs.dlq`

   php artisan kafka:work

   - 默认订阅 `config.defaultTopic`（即 `kafka.connections.default.queue`）

4. **三种 HandlerResult 的输出**：
   - ACK：绿色 `<info>` 标签
   - REQUEUE：黄色 `warn` 标签
   - DLQ：红色 `error` 标签

5. **ServiceProvider 桥接修补**：

**已知待办**：

- ⚠️ **Windows 不支持 pcntl**：开发者在 Windows 上按 Ctrl+C 不会触发 `shouldQuit`，只能 Ctrl+Z 终止进程。**这个缺陷在 Windows 上无法根治**，v0.1 接受并写到 README FAQ。Linux/macOS 用户不受影响。

### 16.12.1 Step 12 收尾 - 修测试矩阵 composer require 表达式

**时间**：2026-08-20 15:02
**目的**：修 GitHub Actions 表达式语法问题。

**问题**：

初版写过：
```yaml
"orchestra/testbench:^${{ matrix.laravel == '8.*' && '6' || (matrix.laravel == '9.*' && '7' || (matrix.laravel == '10.*' && '8' || '9')) }}"
```

GH Actions `${{ }}` 表达式里**不**支持 `&&` `||` 逻辑运算符，文档只支持 `==` / `&&` (JSON 合并) / `||` (JSON 合并)。这里 `&&` `||` 会被当字符串拼接，不会按预期解析。

**修复**：在 matrix 里加一个 `testbench` 字段，每个组合直接给出对应 Testbench 版本号（6/7/8/9）。`composer require` 直接引用 `${{ matrix.testbench }}`，零表达式运算。

```yaml
matrix:
  include:
    - php: '7.4'
      laravel: '8.*'
      testbench: '6.*'
      ...
    - php: '8.1'
      laravel: '11.*'
      testbench: '9.*'
      ...
```

这种"在 matrix 里直接铺好对应关系"是 GH Actions 推荐的写法，避免表达式复杂度爆炸。
